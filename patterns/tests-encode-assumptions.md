# 测试复制假设，真库证伪假设

## 上下文

写校验规则（或任何有 fixture 的代码）时，**作者同时是测试数据的作者**。

于是测试里出现的形态，是作者**脑子里**的形态 —— 而作者脑子里的形态，
正是他误解的那部分。测试通过不是因为规则对，是因为**它和规则共享同一个误解**。

## 问题

单测全绿给出的是错误的信心，而不是信心。

2026-09-19 实测：一晚上写了四条规则，**四条全部单测绿、全部在真产物上错**：

| 规则 | 错法 | 单测为什么没抓到 |
| :--- | :--- | :--- |
| `routingToGraduated` | 只比对 id，漏掉**文件名**形式 | 测试里写的是 id 形式（我以为的形态） |
| `falsifierRatchet` | 用全库计数作基线 | 测试 fixture 与真库同量级，看不出"小工作区永远通过" |
| `falsifierRequired` | 对"创建"即生效 | 造 draft fixture 时没断言它**该豁免** |
| `findUnreachable` | 过滤放在建图之前 | fixture 里没有"指向已毕业条目的条目" |

**四条错法各不相同，成因是同一个**：测试与规则共享了作者的假设。
而真产物里长着作者想不到的形态 —— 文件名锚、CRLF、小工作区、draft 状态、
指向已退役条目的边。

## 方案

### 判据

**规则的验收不能只有单测。至少跑一次真产物。**

### 顺序：先真产物，后单测（不是反过来）

先拿真数据跑 —— 它会在你写测试**之前**告诉你形态长什么样。
反过来的话，你会先写出一套基于错误假设的测试，然后被它的绿色说服。

### 识别信号

**「单测全绿但真产物报错」出现时，先怀疑 fixture 与真产物的形态差异，
不要先怀疑真产物。**

第一反应如果是"真库有问题"或"这个 case 特殊"，就会去加例外 ——
而那正是把 bug 固化成规格。

### 形态清单（本项目实际踩过的）

跑真产物时，专门看这几处 fixture 天然测不到的地方：

- **引用的两种锚**：`[[S13]]`（id）与 `[[S13-Smart-Constructor]]`（文件名）
- **行尾**：Windows 上是 CRLF，`split("\n")` 之后每行都带 `\r`
- **规模**：小 fixture 里恒真的条件（`1 <= 115`）在大工作区里才有意义
- **生命周期**：`draft` 的空骨架 vs `active` 的成品
- **退役状态**：指向已毕业/dormant 条目的边，仍然连接着图上两个节点

## 反面

- **不要**因此不写单测 —— 单测覆盖的是**边界与分支**，它仍然必要；
  只是它**不能作为唯一验收**。
- **不要**把"fixture 造得像真库"当解法 —— 你想不到的形态，
  照你的想象造的 fixture 同样想不到。要的是**真产物**，不是更逼真的布景。
- **不要**在真产物报错时先加例外让它变绿 —— 那会把误解固化成规格。
- **不要**用"真库跑过了"代替单测 —— 真库只覆盖它当下那一种形态，
  分支与边界仍要靠单测。
