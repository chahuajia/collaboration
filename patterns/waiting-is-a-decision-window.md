# 等待是决策窗口，不是空隙

## 上下文

把任务交给 agent 后，有一段**真实存在**的等待。直觉是"别浪费这段时间"，于是去找点别的做。

## 问题

- **上下文切换成本 > 等待成本**：切去做另一件要动脑的事，回来要重建上下文（分钟级），净亏。
  同一上下文的下一环，切回来成本接近零。
- **等待被当成"空隙"** → 系统为了填满它设计更多机制 → 生产"为运行而运行"的仪式。
- **真正的瓶颈被掩盖**：agent 越快，"**等人拍板**"越是瓶颈 —— 而不是"人闲着"。

## 方案

**等待不是空隙，是决策窗口。** 能填的只有「同一上下文的下一环」，而它们恰好都是**只有人能做的**：

| 动作 | 为什么 agent 做不了 |
| :--- | :--- |
| **审阅上一环** | agent 能生成，但不能替你承认"这是我理解的" |
| **拍板下一环** | agent 有默认值，但猜对了是运气 |
| **准备语料 / 喂外部真相** | 实测结论、业务约束 —— agent 无法自己验证的事实 |

### 判据

> **这次等待期间做的事，需要重建上下文吗？** 需要 → 别做。

### 三种长度，三种策略

| 等待长度 | 做什么 |
| :--- | :--- |
| **秒级**（跑命令） | **什么都不做** —— 切走再切回比等更贵 |
| **分钟级**（生成、读一批文件） | 这件事的下一环：审阅 / 拍板 / 备料 |
| **十分钟以上** | 可以开一条**独立**工作线（另一项目、另一功能） |

### 让窗口可用（三条机制）

1. **长任务开始前**，agent 先交"要做什么 + 需要你拍什么" —— 这正是规格阶段。
2. 停下时**集中列**待决事项，不散在回答里（散着 = 人事后才发现）。
3. 结论标 `as-of` 日期 → review 时一眼看出哪条是旧的。

## 反面

- 不要为了"填满等待"去并行另一件需要动脑的事 —— 那是在为焦虑买单。
- 不要假装秒级等待可以被利用（物理限制，不是设计缺陷）。
- 不要把"人闲着"当瓶颈 —— 瓶颈是**没摆出来的决策**。
- 不要用"加更多 agent"解决边界不清的问题：**边界不清时，加 agent 只会让冲突翻倍**。
