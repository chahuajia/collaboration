# 并行不是分派，是让每一份分派都能被确认到达

## 上下文

多任务、且任务还会衍生子任务时，直觉是"派出去并行做"。
本库实测过一次：**投递没有送达，双方都不知道。**

## 问题

- **"派出去" ≠ "已交付"**。没有回执时，"已派出"只是**臆想** —— 与那个永远绿的 `evolution.yml` 同源。
- **上下文不共享**：子 agent 看到的是**陈旧快照**，它会基于旧状态做决定。
- **失败不可见**：溢出、崩溃、中断，在父 agent 侧和"正在思考"长得**一模一样**。
- **协调开销吃掉并行收益**：派 3 个 agent 各做 1 件，若无人能验收，吞吐不升反降。

## 方案

**把"到达"变成文件系统事实**（产物式凭据）。每个派出的任务先落地：

```text
working-memory/tasks/<task>/
  brief.md      ← 任务原文（= 契约：范围、验收标准都在这）
  status.json   ← 机器可读：{ state, heartbeat_at, artifacts, blocker }
  findings.md   ← 产物（**占位即代表"已接收"**）
```

> **铁律：没有 `status.json` / 没有占位产物 = 没有送达。** 不要假设，去查。

### 失败模式与处理

| 失败模式 | 怎么发现 | 怎么办 |
| :--- | :--- | :--- |
| **投递失败** | 没有 `status.json` | 重派或自己做 —— **不要等** |
| **上下文溢出 / 中断 / 崩溃** | `heartbeat_at` 停更 | **从产物续做**（不是从对话续做 —— 对话已经丢了） |
| **做错了** | 父 agent / 人**自己跑验收** | 子 agent 的自述**不算证据** |
| **范围蔓延** | 与 `brief.md` 比对 + `git status` | brief 里写死"只准改这些路径" |

### 父 agent 在等待时该做什么（不是空转）

三件**不可外包**的事：

1. **验收** —— 子 agent 不能验收自己（实测：它写 README 时把不存在的"退出码 2"写了进去）。
2. **边界判定** —— 子 agent 看不到全局（实测：它看到的是陈旧快照）。
3. **集成** —— 把多份产物合成**一致的现状**。

**对称性**：人的等待是**决策窗口**（见 [[patterns/waiting-is-a-decision-window]]）；
父 agent 的等待是**验收窗口**。两者都不是空隙。


### 与极端集群的衔接（加厚切片）

在 [[patterns/extreme-unattended-cluster]] v4 下，并行派出的「可验收投递」默认加厚为：**代码 + 目标测绿证 + status（HEAD）+（若新接通）RUNBOOK 一行**。半截产物不算送达完成。

### 挂起与超时（2026-09-16 实测补充）

**子 agent 有约 1/3 的失败率，而且失败 100% 静默。**
同日实测：`mcp_server` ✅（约 25 分钟）· `fresh_session` ✅（约 15 分钟）
· `arm_a_control` ❌（**30 分钟零产出，无回执**）。

所以**"等它完成"是错的前提** —— 它可能既不失败、也不完成。
必须有一个**外部的超时判据**。

#### 1. 派活时就定超时预算

不是"等它做完"，是"**等到 X 分钟就认定它死了**"。
判据**不能**是"它报告失败"（它可能永远不报告），必须是**外部可观察的**：

| 观察 | 含义 |
| :--- | :--- |
| 回执文件**不存在** | **没送达** |
| 回执存在但 **mtime 停更** | **卡住 / 死了** |
| 产物在**增长** | 活着 |

#### 2. 回执是**心跳**，不是一次性

brief 里要求：**每完成一步就更新一次回执**（不只是开头写一次）。
于是"文件 mtime"成了**无通信下唯一可用的存活信号**。

#### 3. spawn 后**立刻**验回执，再决定等多久

**这次的错**：spawn 完直接 `wait(15min)`，超时才发觉不对 —— 实际浪费 30 分钟。

**正确顺序**：

```text
spawn → short probe（1–2 分钟，查回执在不在）
  ├─ 有回执 → 放心长等（每 X 分钟看一次 mtime）
  └─ 无回执 → 立刻处理：重派，或自己做
```

#### 4. 失败后**不自动重派**，先问"这个任务能不能串行"

- **能** → **自己做**（可靠优先于并行）
- **不能**（例如对照实验需要两个互不污染的执行者）→
  **说明它本来就不该派** —— 失败暴露的是**任务设计**，不是运气

> **能被文件系统验证的任务才适合并行**（产物是文件）。
> 产物是**行为差异**的任务（对照实验、风格判断）**验不了** —— 别派。

## 反面

- 不要把"派出去"当成"已交付"。
- 不要用子 agent 的自述当验收证据。
- 不要并行"写入面重叠"的任务 —— 会互相覆盖，且**没人能复现**。
- 不要为了"看起来在并行"而拆任务：**协调开销大于收益时，串行更快**。
