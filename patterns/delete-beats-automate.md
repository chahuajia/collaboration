# 删掉优于自动化

## 上下文

一大类文档腐烂有同一个形状：**里面写着会变的事实**（计数、清单、状态、HEAD）。
发现它烂了之后，两个直觉会同时出现：

1. 把它**改对**（治标，下次照烂）
2. 把它**自动化**（写生成器 / 加新鲜度检查）

两者都跳过了真正该问的那个问题。

## 问题

**"怎么让它保持新鲜"是错的问题。对的问题是"它该不该在这里"。**

因为自动化一个不必要的数字，是把一个腐烂源换成了一个**要维护的腐烂源**：

- 生成器本身要维护（它就是新代码、新测试、新的失败模式）
- 生成物与手写内容混在一个文件里时，"哪些行能改"变成隐性知识
- 而如果那个数字本来就**没人真的读**，这整个成本是白付的

**判据**：读者真需要这个数时，他会去哪？**如果答案是"他会去跑命令"，
那么这个数不该写在文档里。**

## 方案

### 一、先问存在，再问新鲜

| 顺序 | 问题 | 答"否"的动作 |
| :--- | :--- | :--- |
| 1 | 这个信息**该不该在这个位置**？ | **删掉**（或换成"跑什么命令"） |
| 2 | 该在，且有单一源头？ | **派生**（见 [[patterns/derivation-over-copy]]） |
| 3 | 该在，但**没有**源头？ | 这才轮到生成器 / 新鲜度检查 |

**绝大多数停在第 1 步。** 而第 1 步的成本是 0，第 3 步不是。

### 二、删掉比修好更强

修好是"这次对了"；删掉是"这里再也不会错"。

```
❌ 修：README 写「模式 40 条」→ 改成「模式 52 条」   （下次照烂）
⚠️ 生成：collab stats 生成这一段                       （生成器要维护）
✅ 删：把「模式 40 条」删掉，改为「跑 collab catalog」  （不会烂）
```

### 三、什么时候第 1 步的答案是"该在"

要诚实——**有些数必须在文档里**：

- 它是**决策依据**（读者拿它做判断，不会去跑命令）
- 它**不会变**（历史记录、已归档的轮次报告）
- 它在**具结**（attestation）：声明"我看过、它反映现实"（如新鲜度时间戳）

第三类尤其要小心：**具结类的信息绝不能被自动化** ——
自动刷新一个具结，等于销毁它。一个永远为真的声明不是声明。

## 反面

- **不要**把"删掉"当成"删信息" —— 删的是**文档里的投影**，信息本身在
  `git` / 命令输出 / 生成物里都还在。删的是那个会和源头分叉的副本。
- **不要**因为"写个脚本很简单"就写 —— 脚本的**长期**成本不是它写出来那天。
- **不要**用生成器处理**具结**（"我检查过了"这类声明）。
  生成器能产出数字，产不出"有人真的看过"。
- **不要**反向滥用：**能派生就别删**（`DEFAULT_DIRS = Object.values(EntryKindDir)`
  优于删掉这个常量）。删是当**没有单一源头**时的选项；
  有源头时，[[patterns/derivation-over-copy]] 才是对的。

## 与 derivation-over-copy 的分工

| 情况 | 手段 |
| :--- | :--- |
| 值**必须出现**在同一处，且有源头 | **派生**（`Object.values(X)`） |
| 值**必须出现**，且无源头 | 生成器 + 新鲜度检查（最后手段） |
| 值**不必出现** | **删掉** ← 本条目 |

两者是同一个判断的两侧：**都在问"源头在哪"**，
只是"没有源头"时还有一条更便宜的路 —— **让它不必存在**。
