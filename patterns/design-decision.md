# 设计决策三问

## 上下文

面对非平凡的设计选择——架构、分层、命名、工具选型——需要判断"这个设计好不好"。
直觉上容易陷入"我觉得对"或"别人都这么做"的循环。

## 问题

- **"没设计"被当成"不需要设计"** —— 坏设计伪装成无设计。
- **"设计"被当成"加抽象层"** —— 过度设计。
- **无法判断一个设计决策的好坏** —— 只能凭感觉。

## 方案

### 核心：每个设计决策必须通过"三问"

1. **没有它，我会遇到什么具体问题？**（举一个具体的、来自真实场景的例子）
2. **它的收益是什么？**（能举出具体场景吗？）
3. **它的成本是什么？**（抽象层数、认知负担、维护成本）

### 三问答不上来 = 坏设计

| 答不上的 | 设计类型 |
| :--- | :--- |
| 第 1 问 | **过度设计**（不需要的东西加了） |
| 第 2 问 | **装饰性设计**（为了"好看"而设计） |
| 第 3 问 | **天真设计**（不知道代价） |

### "没设计"也是一种设计

- **"我觉得不需要"不是答案** —— 它也要通过三问。
- **"先做，以后再优化"** —— 也要能说出"以后优化什么"。

### 好设计和坏设计的区别

- **好设计** —— 允许重构为更好的设计。
- **坏设计** —— 必须推翻重做。

## 反面

- 不要用"敏捷""快速迭代"作为跳过设计的理由。
- 不要用"以后可能要"作为加抽象的理由（YAGNI）。
- 不要用"这是最佳实践"作为设计理由（必须针对具体问题）。
- 不要因为"好看/优雅"而设计 —— 那掩盖了真实代价。

# Review 的边际价值随抽象层次变化

## 上下文

AI 让"实现"的边际成本趋近于零，但人的 review 带宽没变。
按"AI 写完 → 用户读代码"的方式协作，review 会成为新瓶颈。

## 问题

- **Review 对象错误** —— 用户读代码实现细节。
- **认知负担与拦截效果成反比** —— 越靠下的细节，review 成本越高、拦截效果越低。
- **假 review** —— 用户凭直觉扫一眼，问题延后到生产环境。

## 方案

### 核心：Review 对象优先级

| 优先级 | 对象 | 拦截什么 |
| :---: | :--- | :--- |
| **1（最高）** | **规格** | 拦截"做错方向" |
| **2** | **测试** | 拦截"行为不符" |
| **3** | **类型/接口** | 拦截"结构错位" |
| **4（最低）** | **实现细节** | 拦截"局部 bug" |

### Review 的边际价值曲线

- **规格** —— 信息密度**最高**，review 成本**最低**。
- **测试** —— 信息密度高，review 成本低。
- **实现** —— 信息密度**最低**，review 成本**最高**。

### 为什么上移

- **AI 输出量大** —— 用户凭直觉扫代码无法真正理解。
- **用户逐渐失去系统的理解** —— "这不是我的项目，是 AI 的"。
- **实现错误和需求错误混在一起** —— 无法定位。

### Review 的本质

**用户 review 的是"意图"，不是"代码"。**

- **测试是意图的一种形式化表达** —— 不是唯一形式。
- **对非技术用户** —— "示例输入输出"比"测试断言"更易 review。

### 五个对策（针对 Vibe Coding 陷阱）

| 陷阱 | 对策 |
| :--- | :--- |
| 测试代码也会爆炸 | 按行为分组、表驱动、`toMatchInlineSnapshot` |
| 测试和实现"同错" | 规格先于测试；测试必须包含反面案例 |
| 迭代不收敛 | 每轮定义收敛目标；最小可验证增量；Timebox |
| 小瀑布风险 | 循环要"足够小"（一次一个行为）、"可中断" |
| 探索任务不适用 | 区分"清晰任务"与"探索任务" |

## 反面

- 不要让用户直接读大段代码。
- 不要把所有任务都塞进这个流程 —— 探索任务先探索。
- 不要用"AI 说它对"替代"我理解它对"。
- 不要让流程僵化 —— 它是骨架，不是监狱。

# 人机协作的层级 Actor 系统

## 上下文

设计"人机协作流程"时，直觉上用"有限状态机（FSM）"建模。
但 FSM 会丢失并行性、异步性和层级结构。

## 问题

- **FSM 假设"全局单一状态"** —— 但人机协作中，人和 AI 各有自己的状态。
- **FSM 是同步的** —— 但实际协作是异步的（你 review 时，AI 可以预写下一个测试）。
- **FSM 是扁平的** —— 但每个状态内部有子状态（如 `SPEC_REVIEW` 内部有"草稿→讨论→定稿"）。

## 方案

### 三层模型的叠加

| 层 | 模型 | 描述 |
| :--- | :--- | :--- |
| **骨架** | **有限状态机（FSM）** | `IDLE → SPEC_REVIEW → TEST_REVIEW → IMPL_REVIEW → DONE` |
| **结构** | **层级状态机（HSM）** | 每个 state 内部有子状态 |
| **动力学** | **Actor 模型** | 用户和 AI 是独立 Actor，通过消息通信 |

### 为什么不是纯 FSM

| FSM | Actor 模型 |
| :--- | :--- |
| 同步状态转移 | **异步消息** |
| 全局状态 | **每个 Actor 有自己的状态** |
| 一次只有一个状态 | **可并行处理多条消息** |
| 转移是即时的 | **转移需要时间**（用户思考、AI 生成） |

### 准确表述

> **"带反馈环的层级 Actor 系统，可以投影为有限状态机来理解骨架，但用 FSM 建模会丢失并行性和异步性。"**

### 五阶段骨架

```text
需求 → 规格 → Review → 测试 → Review → 实现 → Review → 完成
         ↑         ↑                   ↑
         └─────────┴───────────────────┘
              拒绝/新需求回退
```
### 关键设计点

- **FSM 是分析工具，不是实现方式** —— 用它理解结构，别用它固化流程。
    
- **每个 Actor 有自己的内部状态** —— 用户有"理解状态"，AI 有"生成状态"。
    
- **消息是异步的** —— 允许"并行"、"延迟"、"模糊"。
    

## 反面

- 不要把 FSM 当作"流程的最终形态" —— 它是"骨架的投影"。
    
- 不要假设"用户和 AI 同步" —— 它们异步。
    
- 不要让"流程"僵化 —— 它是"骨架"，留出并行/异步/模糊空间。
