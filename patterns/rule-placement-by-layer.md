# 一条规则该住在哪一层

## 上下文

"把领域逻辑收敛到 domain"这句话本身不是判据：同一个改动，
可以说成"把规则放进它数据所在的层"，也可以说成"应用层编排、规则外置"。
只要项目已经分了 `domain / application / infrastructure / interfaces`，
**"什么算越界"就必须写下来** —— 否则同一条规则会在四处有四种写法
（例如骑手接单资格同时存在于实体断言、内存过滤与数据库查询里）。

## 问题

- 没有判据时，模型照"本地最近似的写法"抄：抄到哪一层，取决于它先读到哪个文件。
- 惯例（"规则放域层"）在具体项目里会**悄悄改行为**：例如某项目的聚合 `rehydrate` 会补默认值，
  一旦为了调用聚合方法而 rehydrate，缺字段的文档就换了语义。
- "重复"分两种、动作相反（死副本 vs 活副本），判据缺失时必然做错其中一种。

## 方案

### 一、归属判据（自下而上问，命中即停）

| 问 | 答"是" → 住哪 |
| :--- | :--- |
| 这条规则只依赖它自己那个对象／聚合的字段吗？ | **域层**（谓词 / 断言 / 构造函数） |
| 它给一组读模型算派生值，且算法本身是业务结论吗？ | **域层**（算法一处，读写两侧都调它） |
| 它需要多个聚合协作，或决定"现在做什么"？ | **应用层**，且**只做编排**：取数据 → 调域规则 → 落库 → 发事件 |
| 只有它需要知道数据库语法／驱动细节？ | **基础设施层**，且**由域层声明的数据来翻译**（见三） |

判据必须**自下而上**用：先问"能不能只靠这个对象自己回答"，再问"要不要协作"。
反过来（从用例往下写）会把规则留在用例里 —— 用例越长，规则越藏。

### 二、两个必须显式判断的岔路

| 岔路 | 判据 |
| :--- | :--- |
| 规则要作用于"刚从数据库拿到的文档" | 用**自由函数** `f(doc, ...)`，不要为了调聚合方法而 `rehydrate` —— 先确认默认值不会改变缺失字段的语义 |
| 发现两处"重复" | 先数**消费者**：零消费者 = 死副本，删掉；有消费者 = 活副本，改成引用。两者动作相反，不能都叫"合并重复实现" |

### 三、域问题怎么跨端口（别让用例替数据库说话）

用例里出现 `$in` / `$ne` / `$match` / `$regex`，就是应用层在替数据库说话。两种正确形态：

| 形态 | 什么时候用 |
| :--- | :--- |
| **具名方法** | 问题语义固定、不需要调用方补条件（"还有多少单在飞" → `countActive()`） |
| **域声明 + 翻译函数** | 调用方要补条件（按商家／骑手过滤）→ 域层声明 `RIDER_DISPATCH_CRITERIA`，仓储把它翻成 `$ne` |

**命名判据**：方法名必须是**领域问题**，不是查询形状（`countByStatusIn`）。
名字一旦变成查询形状，用例就又开始懂数据库了。

**什么时候不套用**：当"带条件的域问题"需要一场景一个方法时，先停下来定命名；
否则等于用一堆一次性方法替换一处泄漏，熵不降反升。

### 四、判据本身怎么验证

- 收敛后必须有一条测试断言**两个入口选出同一批对象**（数据库过滤 vs 域谓词，含字段缺失的文档）。
- 报错文案属对外契约：搬动规则时逐字保留，规格里钉死。
- 已知的、够不到的分歧（如 `isActive: 1` 这种非布尔真值）**写成测试记录**，不要顺手"修掉"。
- 用**只暴露该具名方法**的假仓储写规格：用例若退回自己拼 filter（改调 `count({...})`），
  假仓储会因方法缺失而炸 —— 这锁的是分层**方向**，不只是返回值。

## 反面

- 不要把"编排"当"规则"留在用例里。
- 不要把 `$ne` / `$in` / 字段名拼写这类持久化语法带进域层 —— 域层声明**期望**，不声明**查询**。
- 不要为了"让规则更像聚合"而 `rehydrate`。
- 不要因为"两处代码像"就合并：先数消费者。
- 不要在**同一轮**里既搬规则又改行为：两者混在一起后，回归与有意变更就无法区分（见 [[characterization-first-refactor]]）。
