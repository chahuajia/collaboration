# Review 的边际价值随抽象层次变化

## 上下文

AI 让"实现"的边际成本趋近于零 —— 但人的 review 带宽没变。
按"AI 写完 → 用户读代码"的方式协作，review 会成为新瓶颈，
并被形式化 —— 用户扫一眼就放过，问题延后到生产环境。

## 问题

- **Review 对象错误** —— 用户读实现细节（信息密度最低、成本最高）。
- **认知负担与拦截效果成反比** —— 越靠下的细节，越难 review，拦截效果越差。
- **假 review** —— 用户凭直觉扫代码，问题延后。
- **用户失去系统理解** —— "这不是我的项目，是 AI 的"。

## 方案

### 一、四层 Review 对象（按边际价值降序）

| 优先级 | 对象 | 信息密度 | Review 成本 | 拦截什么 |
| :---: | :--- | :---: | :---: | :--- |
| **1** | **规格**（自然语言/示例/伪代码） | **极高** | **极低** | 做错方向 |
| **2** | **测试**（规格的形式化） | 高 | 低 | 行为不符 |
| **3** | **类型/接口**（结构与契约） | 中 | 中 | 结构错位 |
| **4** | **实现细节**（算法/局部逻辑） | **低** | **高** | 局部 bug |

### 二、边际价值曲线（量化表达）
边际价值  
│  
高 │ ★ 规格  
│  
│ ★ 测试  
│  
│ ★ 类型  
│  
低 │ ★ 实现  
└──────────────────────→ 抽象层次（低→高）

**关键结论**：
- **每上移一层** —— review 的边际价值**增加 3-5 倍**。
- **每下移一层** —— review 成本**增加 3-5 倍**。
- **"规格"review 一次** —— 拦截"方向错" —— 等价于"读 1000 行代码"。

### 三、为什么"上移"

- **AI 输出量大** —— 用户无法"读完 500 行"。
- **用户的"意图 review"被淹没** —— 实现细节占据注意力。
- **错误定位成本上升** —— 实现错误和需求错误混在一起。
- **系统理解流失** —— 用户逐渐"只看结果"。

### 四、五个对策（Vibe Coding 陷阱）

| 陷阱 | 症状 | 对策 |
| :--- | :--- | :--- |
| **测试代码也会爆炸** | 20 个测试 = 500 行 | 按行为分组、表驱动、`toMatchInlineSnapshot` |
| **测试和实现"同错"** | AI 误解需求 → 测试也错 | 规格先于测试；测试必须包含反面案例 |
| **迭代不收敛** | "用户觉得不行 → 反复" 无限循环 | 每轮定义收敛目标；最小可验证增量；Timebox |
| **小瀑布风险** | 规格→测试→实现，一次性 | 循环要"足够小"（一次一个行为）、"可中断" |
| **探索任务不适用** | 需求模糊时无法写测试 | 区分"清晰任务"与"探索任务" |

### 五、Review 的本质

**用户 review 的是"意图"，不是"代码"。**

- **测试是意图的一种形式化表达** —— 不是唯一形式。
- **对非技术用户** —— "示例输入输出"比"测试断言"更易 review。
- **对技术用户** —— "规格 + 测试标题"比"实现代码"更易 review。

### 六、实操：什么时候该 review 什么

| 用户类型 | 优先 review | 可以跳过 |
| :--- | :--- | :--- |
| **产品经理** | 规格 + 示例 | 测试 / 类型 / 实现 |
| **技术负责人** | 规格 + 测试 + 类型 | 实现细节 |
| **代码审查者** | 类型 + 关键实现 | 测试（如果已过 CI） |
| **运维** | 接口 + 配置 | 其他 |

**"谁 review 什么"** —— 按"角色 × 优先级"矩阵。

### 七、与 A10 的关联

**A10 说的"上移"** —— 就是本 pattern 的**直接应用**：

- **A10 的"上移"** = "向 What 移动" = "向规格/测试移动"
- **A10 的"五阶段"** = "每次 review 一个层次的产出"
- **A10 的"回退"** = "下游失败 → 回上游"

**本 pattern 是 A10 的"为什么"** —— 它解释了"为什么要上移"。

## 反面

- **不要**让用户直接读大段代码。
- **不要**把所有任务都塞进这个流程 —— 探索任务先探索。
- **不要**用"AI 说它对"替代"我理解它对"。
- **不要**让流程僵化 —— 它是骨架，不是监狱。
- **不要**忽略"用户类型" —— 不同角色 review 不同层。
