# 什么时候该派子智能体（以及为什么它们会白跑）

## 上下文

长任务里把工作分给"子智能体"看起来很划算：并行、隔离上下文、不占主上下文。但**派出去的不是劳动，而是"一个新的、缺上下文的执行者"**——
它看不到你积累的判据、踩过的坑、以及刚刚验证过的事实。于是失败往往不是"做错"，而是"**跑了很久、什么都没留下**"。

## 问题

本会话实测（一次任务里派了 4 个子智能体）：

- 4 个全部停在 `inactive`，**背景作业 0**，**没有任何可交付物**；其中两个**根本跑不了 `node`**（沙箱限制）。
- 结果是**我自己把活重做了一遍**，而它们作为**永久记录**留在会话里，让后来者（人）困惑："为什么挂着四个？它们还在跑吗？"
- 共同特征：它们被派去做的，是**需要仓库门禁才能验证**（跑 lint/tsc/test）或**一次 grep/read 就能完成**的侦察与搬迁。

## 方案

派子智能体前，逐条过闸；**任一不满足就不派**：

1. **它自己能验证**：任务必须包含"用什么命令证明做对了"。若它跑不了那些命令（无 node / 无网络），**派了必白跑**——因为产出无法被证明。
2. **自足**：不需要本会话的上下文（判据、刚验证过的事实、隐藏约束）。需要 → 用 `subagent_fork`（继承上下文），或干脆自己做。
3. **不替代一次调用能做完的事**：一次 `grep`/`read` 能拿到的答案，派出去要付"上下文交接 + 一个完整回合"的代价。
4. **有界**：写清停止条件与**必须留下的产物**（文件路径 + 验证输出）。没有"必须留下的产物"这一条，就会出现"跑了很久、无 durable 变更"。
5. **不派结构性与不可逆操作**（搬迁/删除/改配置）：这类操作靠"每次失败换来的硬规则"（文件级移动、门禁绿后再删源、引号无关、按 basename 搜消费者…），**不是靠一个新执行者的直觉**。
6. **预算账**：一个子智能体 ≈ 一次完整回合 + 交接损耗。**并行收益只有在"任务彼此独立且都能自验"时才为正。**

## 反面

- **"多派几个更保险"** ✗ —— 每个都会留下永久记录（本平台没有"删除子智能体"的工具，只有 `interrupt`／`send_message`），无产出的记录会污染后来者的判断。
- **派出去当"侦察兵"** ✗ —— 侦察的价值恰恰在于**共享你已知的约束**；换一个没有约束的人去侦察，回来的多半是泛泛之谈。
- **用子智能体绕开自己的纪律**（例如"让它去搬文件吧"）✗ —— 门禁与硬规则不会随任务一起被派过去。
- 例外：**明确可自验、彼此独立、互不依赖主上下文**的批量工作（例如"对 N 个文件各写一条特征测试并跑通"）——这才是它真正划算的地方。
