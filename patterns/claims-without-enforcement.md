# 声称需要被强制，否则会静默漂移

## 上下文

代码里有一类注释，不描述"这段代码做什么"，而是**声称一个跨切面的属性**：

```java
/** 换电用例：取站 → 领域换电 → <strong>同事务双写</strong>（存站 + 追加换电日志）→ 返回会话。 */
/** 本方法线程安全。 */
/** 调用方须保证 id 唯一。 */
/** 返回值已按 createdAt 升序。 */
```

读起来像事实，实际是**一句承诺**。而承诺与事实之间，隔着一个没人检查的假设。

## 问题

**注释声称的属性，若无任何东西强制它，它一定会漂移 —— 而且漂移是静默的。**

- **没人会收到通知**。注释不会编译失败，测试不会变红，日志不会报警。
- **它读起来像事实**。下一个人（下一个模型）会**基于它**写代码，而不是去验证它。
- **失效代价可能很高**。跨切面属性往往是"出错时数据已经坏了"的那一类。

实测（2026-09-19）：

`PerformSwap` 的 javadoc 写着"**同事务双写**"，而**全仓没有一处 `@Transactional`**。
于是站库存与换电日志各写各的事务 —— 第二次写失败时第一次**已提交**：
站里的电池被取走，换电日志没有记录。

**后果不是慢，是数据错**，而且用户那一侧看起来一切正常（没有异常逃出来）。

> 关键：这条注释**不是错的当时就错了**。它可能是"打算这么做"写下的，
> 后来实现没跟上；也可能实现过、被重构掉了。**没有机制的东西，
> 正确与否只取决于没人动它。**

## 方案

### 一、读到声称时：先问"谁在强制它"

**一条 grep 就够**。声称"同事务"→ 找 `@Transactional`；声称"线程安全"→
找锁 / 不可变 / `Concurrent*`；声称"已校验"→ 找校验发生的位置。

```bash
grep -rn "@Transactional" src/main/java   # 空 = 声称无人兑现
```

**成本 5 秒，收益是避免基于假事实往下建。**

### 二、判定"注释 + 强制"还是"注释 - 强制"

| 情形 | 动作 |
| :--- | :--- |
| 有强制（注解 / 测试 / 类型） | 注释是**指路**，保留并让注释指向机制 |
| 无强制，但**该有** | **加机制**（如 `@Transactional`），并写一个**能否证它**的测试 |
| 无强制，且**不该有** | **改注释**（别改成更委婉的说法 —— 删掉那个声称） |

### 三、加机制时，先写**红测试**证明它现在不成立

这是顺序问题，也是 [[patterns/tests-encode-assumptions]] 的顺序：
**先证明它是坏的，再修**。

步骤：
1. 造一个能让"第二次写"失败的输入（mock 抛异常）
2. 断言"第一次写被回滚" —— **此时它会红**
3. 再加机制，看它变绿

第 2 步的价值：它把"注释可能是错的"变成**已证的缺陷**。
跳过它，你只是"加了个注解"，没人知道原来那个是不是真的坏了。

### 四、自己写这类注释时

**要么在注释里写清"由谁强制"，要么别写这个声称。**

```java
// ❌ 声称无出处
/** 同事务双写 */

// ✅ 指向机制（机制被删时这里也失效，但至少可追）
/** 两次写的原子性由 {@link TransactionalPerformSwap} 保证 */
```

## 反面

- **不要**因为"注释写了"就相信 —— 包括你自己刚写的。**写的人最容易信。**
- **不要**用"改成更弱的措辞"来修（"双写"→"顺序写"）。弱化措辞不解决数据错，
  只让错更难被发现。要么加机制，要么**删掉这个声称**。
- **不要**只在被问到时才查 —— 它漂移的时刻你不在场。
- **不要**把它与 [[patterns/policy-without-mechanism]] 混为一谈：
  那条讲的是**流程政策**缺机制 → 更慢（负优化）；
  这条讲的是**代码声称**缺机制 → 更错（静默数据损坏）。**失效模式不同，修法也不同。**
