# 修剪策略

## 上下文

知识库只增不减必然腐烂[[patterns/entropy-reduction]]。但**修剪本身是有成本的**：
删错东西的代价，往往高于多留一条的代价。
所以问题不是"要不要删"，而是"**凭什么判它该走**"。

## 问题

- 原规则"6 个月未被引用 → dormant，再 6 个月 → 删除"是**一刀切**：
  - 它把"暂时没人用"和"没用"当成一回事。
  - "未被引用"需要测量，而从未有人测量过——所以这条规则实际上从未执行。
  - 时间不是原因，只是代理指标；用时间代替判断，等于放弃判断。
  - 若只有「应修剪」的文字、从无可达性扫描产物 → 属于 [[patterns/policy-without-mechanism]]（有政策无机制）。

## 方案

### 零、先读这张表：哪些是机制，哪些只是政策

**2026-09-26 逐条审计。** 判据来自 [[patterns/policy-without-mechanism]]：
**没有仪器 = 从未执行**，写了字不等于生效。

| 主张 | 现状 | 仪器（接在哪） | 证据 |
| :--- | :--- | :--- | :--- |
| 标记-清除（找孤岛） | ✅ **有机制 + 有实证** | `collab retire --candidates`（种子 = 根文档，无向；默认 30 天宽限；只报告不写盘） | 三种读法实测 0 / 1 / 24 条 → 采用无向（见下「读法歧义」）；真库扫出 1 条 → [[patterns/catalyst-nodes]] 退役（v4.9.5） |
| 休眠 `dormant`（退出路由索引） | ✅ 有机制 + 用过 | `collab retire <id> --dormant --reason` | 现存 2 条 `status: dormant`；退役后由 `isRouted` 统一判出索引 |
| 毕业 `enforced` | ✅ 有机制 + 用过 | `collab retire <id> --enforced <路径> --confirm --reason` + `--check-enforced` 复查目标仍在 | 3 条毕业：`domain-purity-is-structural` / `S13` / `S34`（各自有架构测试固化） |
| `--reason` 强制四分类 | ✅ 有机制 | CLI 层（不是散文） | 漏填 `--reason` 直接报错 |
| 结构性决策 → ADR | ✅ 有机制 | `meta/decision-records/`（`ADR-0001`…`ADR-0012`） | 12 条 ADR |
| 修剪决策写 `evolution-log` | 🔶 人写过，**无强制** | 无 —— 靠人 | `v4.9.1` 首次毕业、`v4.9.5` 标记-清除落地 |
| **分代**（新生 / 中生 / 老生） | ❌ **纯散文** | 无字段、无命令、无测试 | 三个月来从未执行 |
| **热 / 冷分级 + `archive/`** | ❌ **纯散文** | 仓库里**没有 `archive/` 目录**，无命令 | 同上 |
| 「引用计数 = 0 且 > 6 个月」 | ❌ 无独立仪器（已被标记-清除取代） | 入度/出度只在 `retire --candidates` 内部算 | 旧版本自认「从未有人测量」 |
| 「重叠 ≥ 50% → 合并候选」 | ❌ 无机制 | 无相似度测量；[[W12-条目合并]] 靠人判 | — |
| 「被 ≥ 3 个 fork 引用 → 提升」 | ❌ 无测量（社区尚未发生） | 无 | 可接受，但**别当已生效** |
| 「某分支 ≥ 7 条 → 建子目录」 | ❌ 无机制 | 无计数器 | — |
| 「新增 3 条 → 处理 1 条」代谢配额 | ❌ **无机制** | 代码里只有 `AGREEMENT_LIMIT = 10` —— 那是**约定数量上限**，不是 3:1 配额 | [[patterns/policy-without-mechanism]] 已列为「从未执行」 |
| 社区同步（fork 拉取 / 提升） | ❌ 未实现 | `collab sync` 不存在 | 本文下方已标注 |

**用法**：只有 ✅ 行可以直接当「已生效」引用；🔶 行要写「靠人做」；❌ 行必须带
「未实现 / 计划」，或先装仪器再谈。**这份审计本身就是本库的判据 8 用在自己身上。**

### 一、两种修剪：标记-清除 + 分代

| 机制 | 做法 | 解决什么 |
| :--- | :--- | :--- |
| **标记-清除** ✅ | 种子 = **根文档**（`ROOT.md` / `AGENTS.md` / `README.md`），沿 `[[…]]` **无向**遍历，可达的标记为活；不可达的进入候选。**命令**：`collab retire --candidates` | 找出"没人指向、也没指向谁"的孤岛条目 |
| **分代** ❌ 未实现 | 新生代（<1 个月，每条都评审）→ 中生代（1-6 个月，抽查）→ 老生代（>6 个月且被引用，**改动成本最高**，改前必须 ADR） | 让评审成本花在真正在变的部分 —— **但今天没有任何东西在读它**，评审节奏仍是"想到了就做" |
| **热/冷分级** ❌ 未实现 | 热＝在索引里；温＝文件在但不在主索引；冷＝移入 `archive/`，退出索引 | 把"体积成本"和"存在性"分开 —— **`archive/` 目录不存在**；今天实际只有「在索引 / `dormant`（退出索引但文件仍在原位）」两档 |

**关键区分：从索引除名 ≠ 删除。**
git 是基因库——任何删除都在历史里，随时可复活。所以"退出当前环境"的成本接近于零，
不需要为了"万一以后有用"而保留它在索引里占位（占位成本才是真正的成本）。

#### 读法歧义（2026-09-19 裁决）

本节原文写"从 `ROOT.md` / **`_index.md`** / 被引用条目出发"。**字面照做是空操作** ——
`checkIndexForward` 保证每条目都在自己的 `_index.md` 里，而同一张索引表里的条目
彼此连通，于是全图成为一个连通分量。

实测（`collab-cli/working-memory/reach-check.cjs`，可重跑）：

| 读法 | 扫出 |
| :--- | :--- |
| A：`_index.md` 也是种子 | **0 条** ← 空操作，与 `known-gaps` 里"规则写了从未执行"同构 |
| B：种子 = 根文档，**无向** | **1 条** |
| C：种子 = 根文档，**有向** | 24 条（含 `A20`/`A21` 等明显还活着的条目） |

**采用 B。** 理由：

1. **索引不进图** —— 索引成员资格是另一条已被强制的轴（`MISSING_FROM_INDEX`），
   混进可达性会让它变成同义反复。
2. **无向** —— 要抓的是"没人指向、也没指向谁"的**孤立分量**，
   那正是弱连通的定义。有向读法被"条目普遍向上引用枢纽"的结构打偏：
   它把"没被根文档**直接**引用"误当成"没人引用"。
3. **宁可少报** —— 有向的 24 条里混着活条目；多报会让人干脆不看这个报告，
   那比不报更坏。少报的代价是人再审一遍，可控。

**孤岛 ≠ 该删。** 新写的条目还没轮到被引用，也是孤岛。所以
`collab retire --candidates` 默认带 **30 天宽限**（`--grace-days` 可调），
且只输出**理由**（入度/出度），不下结论 —— 退役仍要人逐条给 `--reason`（§三）。

### 二、删除前必须分类（不许一刀切）

发现一个候选条目后，先判断它属于哪一类，**不同类不同处理**：

| 类型 | 判断 | 处理 |
| :--- | :--- | :--- |
| **过时** | 内容曾经对，但现在错了 | 改写成新结论，或标 `deprecated` 并指向替代条目 |
| **重复** | 与另一条目重叠 ≥ 50% | 合并，保留被引用更多的那条 id |
| **表达差** | 内容对，但没人找得到/看不懂 | **改写，不删**（问题在检索，不在内容） |
| **未成熟** | 可能有用，但没验证过 | 降到"温"或"冷"，退出主索引，等它被需要时复活 |

**判据**：如果一个候选项你只能说出"它写得挺久/挺用心"，那它属于未成熟——降级，不是删除。

### 三、每个修剪决策要写一句"为什么"

修剪不能只留动作，要留判断依据（承接 A8 三问，用在条目自己身上）：

> `<条目 id>`：判为 **过时 / 重复 / 表达差 / 未成熟**，因为 `<具体证据>`，动作 `<改写/合并/改索引/降级>`。

记录追加到 `meta/evolution-log.md`——**删除也是一次正式的演化决策**。

### 四、量化触发（仍然需要，但不单独用）

> ⚠️ **本节 6 行里只有 1 行有机制。** 其余 5 行是**待装仪器的方向**，不是当前行为 ——
> 现状见上面的「机制成熟度」表。写进别的文档时请带这一句。

| 信号 | 动作 |
| :--- | :--- |
| 两条目重叠 ≥ 50% | 合并候选 |
| 引用计数 = 0 且 > 6 个月 | 标记-清除候选（**不是删除**） |
| 被 ≥ 3 个 fork / 项目引用 | 提升为独立条目 |
| 某分支 ≥ 7 个条目 | 建子目录 |
| 结构性决策 | 写 ADR |
| **新增 3 条 → 处理 1 条** | 代谢配额：防止只增不减 |

## 反面

- 不要用"时间"代替"判断"——时间只是线索，不是理由。
- 不要因为"写了很久/挺用心"就保留——沉没成本不是依据。
- 不要"删除即销毁"——删除 = 退出索引，git 保留基因。
- 不要频繁重构目录结构——结构稳定本身就是价值。
- 不要一次清空"所有 dormant"——先分类，再分批处理。

## 社区同步策略

- 主干合并后，fork 通过同步拉取（`collab sync` **尚未实现** —— 见 [[S10-collab-cli]]）。
- 若某条目被 ≥ 3 个 fork 引用 → 提升为独立技能。
- 若某条目在主干 dormant 但在 ≥ 1 个 fork active → 先讨论再决定（多数派的"没人用"可能是少数派的刚需）。
- 主干定期扫描 fork，吸收高价值条目（见 `patterns/horizontal-gene-transfer`）。
