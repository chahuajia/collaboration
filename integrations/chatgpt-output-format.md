# chatgpt-like：输出格式约定

> 本条目原为 `A17-对话式AI输出格式约定`（约定层）。
> 2026-09-16 迁入集成层：**它描述的是"对话式 AI 这个特定环境怎么输出"，不是通用协作规则**。

## 上下文

对话式 AI 的输出需要被用户复制/落盘。但输出格式不一致——有时包裹 markdown，有时不包裹，用户操作困难。**额外的问题**：连"分隔符"也会被滥用——短小内容用重型分隔符，反而增加噪音。

## 问题

- 完整文件内容被 ` ```markdown ` 包裹，用户要手动去掉包裹层。
    
- 多个文件一次性输出时，用户分不清文件边界。
    
- 代码片段和文件内容混在一起，判据不清。
    
- **短小内容被重型分隔符标识，视觉噪音过大。**
    

## 方案

### 核心判据：主体 vs 引用

**包裹的目的**：与周围文字区分。

|内容性质|是否包裹|理由|
|---|---|---|
|回答主体 = 一个完整文件|❌ 不包裹|用户直接全选复制|
|回答主体 = 多个文件|❌ 不包裹|用分隔符标识边界|
|回答中的代码片段|✅ 包裹|与文字区分 + 语法高亮 + 复制按钮|
|回答中的文件内容"引用"|✅ 包裹|它是引用，不是主体|

**判据**：**包裹的判据不是"内容是不是代码"，而是"它是主体还是引用"。**

### 分隔符的三级标准

**核心原则**：**分隔符的"重量"应与内容的"规模"匹配。**

|场景|分隔符形式|例子|
|---|---|---|
|**单文件 / 单片段**|不用标记（回答本身就是它）|输出一个测试文件|
|**2-5 个短文件**|`### <文件名>` 作为 H3 标题|3 个测试文件（每个 < 200 行）|
|**多文件 / 长内容 / 跨域输出**|`===== FILE: <相对路径> =====`|COLLABORATION 条目批量输出|

**判据**：

- **内容的边界"一眼可见"吗？** → 可见则用 H3；不可见则用 `===== FILE`。
    
- **是 COLLABORATION 内容吗？** → 是则默认用 `===== FILE`。
    
- **是代码文件吗？** → 短则用 H3，长或多则考虑 `===== FILE`。
    

### 为什么 COLLABORATION 内容用 `===== FILE`

**原因**：COLLABORATION 条目**每个 100-300 行**，且**一次输出多个**——边界"一眼看不清"。**用户需要精确切分到不同文件**。`===== FILE` 提供了：

- **视觉标记给人看**（机器切分改由 frontmatter 承担 —— 见下节与 [[ADR-0012]]）。
    
- **视觉上强边界**（用户手动切分）。
    
- **包含路径**（用户不需要记忆"这个内容该存哪"）。
    

### 为什么代码文件不用 `===== FILE`

**原因**：

- **代码文件短**（几十到两百行），边界本身就清晰。
    
- **用户知道每个文件该存哪**（IDE 会提示）。
    
- **`===== FILE` 在短内容里视觉过重**——它把"一行文件头"变成"三行包裹"，噪音比价值大。
    

### 条目边界协议（多文件输出，2026-09-26 改）

**契约是条目自己的 frontmatter，不是人为分隔符。**

```
---
id: lenient-parsing      ← 文件名由 id 决定
type: pattern            ← 目录由 type 决定
status: active
---

## 正文示例
...
```

| | 2026-09-26 之前 | 现在 |
| :--- | :--- | :--- |
| 块边界 | `===== FILE:` / `===== END FILE` 成对标记 | 自描述 frontmatter（`---` … `---`） |
| 路径 | 随文本带来 | **派生**：`type` → 目录，`id` → 文件名 |
| 块外散文 | 整单拒收 | **天然跳过**（并 warn 跳过了什么） |
| `===== FILE:` | 必须 | **可选冗余**（帮人眼切分；路径以 frontmatter 为准） |

于是 AI 顺手加的东西（开场白、` ``` ` 围栏、协议示例块、合规说明表、结尾追问）
**原样粘贴即可**：`collab parse <粘贴存成的 txt>` → `collab apply`。
被跳过的块会打 warning（`PARSE_SKIPPED_BLOCK`）—— **宽容不等于静默**。

**为什么改**：实测（2026-09-26）AI 交出来的是「开场白 + 围栏 + 真条目 + 协议示例 + 说明表」。
旧协议只认 `===== FILE:`，于是**整单拒收**（15 条 `content outside any block`）。
约定的形状不对时，加宽容规则追不上：换一个模型就要再打一个补丁（[[patterns/lenient-parsing]]）。

### 与 A15 的关系

A15 说"批处理写入"——用户一次写入多个文件。本约定的"三级标准"是 A15 的具体形式。

## 反面

- 不要包裹"回答主体就是一个文件"的内容——多此一举。
    
- **不要为短小内容用重型分隔符**——那会增加噪音。
    
- 不要在多文件输出时不用分隔符——用户分不清边界。
    
- 不要为一行代码用块级包裹——用行内代码。
    
- **不要为代码文件用 `===== FILE`**——那应该用于 COLLABORATION 内容。
    
- **不要把 `===== FILE:` 当契约**——机器认的是 frontmatter（`type` + `id`）；标记与它不一致时以 frontmatter 为准。
    
- **不要为了"格式合规"去裁剪自己的输出**——开场白、围栏、说明表都无妨，工具会跳过它们。
