# S34 边界层与领域的错误翻译

## 上下文

领域层的错误以**类型化**的形式（如 `Issue`）返回。
边界层（CLI）需要把它**翻译**成"用户可读的消息" —— 通常 `throw new Error(...)`。

## 问题

- **重复实现校验**：CLI 层和领域层都实现"同一条规则"——**必然漂移**。
- **消息格式不一致**：两处错误消息的格式不同 —— 用户困惑。
- **翻译缺失**：领域返回 `Result` —— CLI 层忘了 `if (!result.ok) throw`。

## 方案

### 一、领域是"权威校验"的唯一来源

- **CLI 层不重复实现校验**。
- **CLI 层调用 `EntryId.create` / `Frontmatter.create`** —— 让领域做。
- **CLI 层只负责"翻译"** —— `Result → Error`。

### 二、翻译的标准模式

```ts
const result = EntryId.create(idArg, type);
if (!result.ok) {
  const issue = result.error;
  const suffix = issue.suggestion ? `\n  → ${issue.suggestion}` : '';
  throw new Error(issue.message + suffix);
}
```
**关键**：

- **`issue.message`** —— 用领域的消息（单一真相源）。
    
- **`issue.suggestion`** —— 用领域的建议（帮助用户）。
    

### 三、错误消息的层次

|层|内容|例子|
|---|---|---|
|**领域**|事实 + 建议|`id "X12" must start with "S"...` + `rename to "SX12"`|
|**CLI**|事实 + 建议（透传）|同上（加 `→` 前缀）|
|**用户**|事实 + 建议 + 下一步|同上 + "或运行 `collab --help`"|

**CLI 不该"重新组织"领域的消息** —— 该"透传 + 加 CLI 特有的下一步"。

### 四、常见漂移的防止

**契约变化时** —— **检查"两处校验"是否同步**。

**判据**：**"如果只改一处，另一处会怎样？"**

- **能发现** → 已同步（或至少一致）。
    
- **不能发现** → 有漂移风险。
    


## HTTP / DomainOutcome 扩展（evo-collab-extreme 切片4）

领域以 **类型化错误码**（`DomainOutcome.Err` / `DomainErrorCode`）返回时，边界层（Controller）同样只做翻译，不做二次校验：

1. **按错误码映射 HTTP 状态**（冲突类 → 409，其余业务不可处理 → 422），禁止 `message.startsWith` / 文案嗅探。
2. **suggestion 可在边界附加**，但 `error` 字段应是领域码（或领域 message），不是边界自造同义词。
3. **翻译器按限界上下文分立**：换电站 `SwapApiErrorTranslator` 与权益换电 `EntitledSwapApiErrorTranslator` 不可混用——把 ENTITLEMENT_* 误映射成站级 CONFLICT，会教客户端错误重试。

判据：**只改领域码枚举或翻译表一处，HTTP 契约是否跟着变？** 能发现 → 已同步。

## 反面

- 不要在 CLI 层重复实现领域的校验规则。
    
- 不要重新组织领域的错误消息（除非加 CLI 特有的上下文）。
    
- 不要让两处错误消息格式不同。

- 不要用领域 message 前缀/文案嗎探猜 HTTP 状态码；不要跨限界上下文复用错误翻译器。
