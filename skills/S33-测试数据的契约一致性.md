# S33 测试数据的契约一致性

## 上下文

写测试时需要构造"测试数据"（fixture）—— 它**必须符合生产代码的契约**。
契约变化时，测试数据可能"看起来还能用"但"实际已经不合法"。

## 问题

- **手工 stub**：`{ frontmatter: { id: 'S1' } } as Entry` —— 缺字段、类型不对。
- **契约变化后过时**：如"条目 = 有 frontmatter 的 `.md`"变严后，空文件不再合法。
- **遗漏**：多条测试数据里，只有部分被更新。
- **反复失败**：逐个遇、逐个修，反复打断。

## 方案

### 一、用工厂，不手写 stub

- **有工厂**（`makeEntry` / `writeSkill`） → **用工厂**。
- **无工厂** → 才手写，但**模仿完整接口**。
- **不用 `as` 断言绕过** —— 断言掩盖"类型不匹配"。

### 二、从特征推断，不手工标全字段

**例**：测试数据的 `type` 从 `path` 推断（`skills/S1.md` → `Skill`）。

```ts
type: e.type ?? inferTypeFromPath(e.path),
```
**减少手工字段** = **减少遗漏**。

### 三、契约变化时"主动扫描"

**契约变化后，扫三类**：
|类|检查|
|---|---|
|**实现**|编译器|
|**断言**|跑测试|
|**数据**|**`grep` 手写数据构造点** ← 最易漏|

### 四、"拔一棵 ≠ 拔一片"
**发现同类 bug 时的最小动作**：

1. **grep** —— 找同类（**第一动作**）。
    
2. **修全部** —— 一次改完。
    
3. **跑测试** —— 一次验证。
    

**三个动作的顺序不可颠倒**。

## 反面

- 不要用 `as` 断言绕过类型检查。
    
- 不要逐条遇、逐条修 —— 先扫描。
    
- 不要让"过时的测试数据"继续使用。
    
- 不要契约变化后只改"报错的那一个"。
