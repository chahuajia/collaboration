# S32 数据变更管理原则

## 上下文

当"数据规则"变更（如枚举收紧、字段必填）时——
旧数据可能不合法 —— 需要主动"盘库"。

## 问题

- **被动修复** —— 等测试"碰巧暴露"，一个个修。
- **漏盘库** —— 只盘生产数据，漏测试数据（或反之）。
- **重复劳动** —— 一个个文件手改。

## 方案

### 一、规则变更的触发

**判据**："这条变更会破坏向后兼容吗？"

- **收紧**（加必填、禁某值） → ✅ **必须盘库**。
- **放宽**（去必填、加允许值） → 旧数据仍合法 → 不必盘库。

### 二、盘库的三层

| 层 | 范围 | 工具 |
| :--- | :--- | :--- |
| **生产数据** | 真实仓库 | 迁移脚本 + `--dry-run` |
| **测试 fixture** | `__tests__/` | `grep` + 批量改 |
| **文档/示例** | README、COLLABORATION | `grep` |

**三层都要扫** —— 不只生产。

### 三、迁移脚本的纪律

1. **先 `--dry-run`** —— 看会改什么。
2. **保留隐式特征** —— BOM、换行、编码。
3. **限定范围** —— 只处理"该处理"的目录（不用宽泛判据）。
4. **可追溯** —— 推断值标注来源（`git log` / 占位符）。

### 四、扫描的关键词

变更规则后，`grep` 这些：

```powershell
Get-ChildItem -Path src -Recurse -Filter *.ts |
  Select-String -Pattern "<旧值>|<旧字段>"

```
  **结果分类**：**该改 / 无影响 / 待判断**。

## 反面

- 不要"看到测试挂了才改" —— 主动盘库。
    
- 不要"只扫生产数据" —— 测试数据也要扫。
    
- 不要用宽泛判据（"所有 .md"）—— 会误伤。
